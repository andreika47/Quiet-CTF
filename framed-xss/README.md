Флаг в куке, с заданным атрибутом `domain`. Бот с этой кукой переходит по ссылке `url`. Сама ссылку бот получает от нас:

Похоже, что нам нужно искать XSS.

В корне приложения раздается JavaScript, который делает `fetch` запрос на `/view`. Ответ сохраняется в `srcdoc` создаваемого `iframe` с включенным `sandbox`. Песочница должна предотвращять выполнение скриптов в `iframe`:
*app.py*
```
<body>
  <h1>XSS Challenge</h1>
  <form action="/">
    <textarea name="html" rows="4" cols="36"></textarea>
    <button type="submit">Render</button>
  <form>
  <script type="module">
    const html = await fetch("/view" + location.search, {
      headers: { "From-Fetch": "1" },
    }).then((r) => r.text());
    if (html) {
      document.forms[0].html.value = html;
      const iframe = document.createElement("iframe");
      iframe.setAttribute("sandbox", "");
      iframe.srcdoc = html;
      document.body.append(iframe);
    }
  </script>
</body>
```
В `fetch` запросе явно добавляется заголовок `From-Fetch`, наличие которого проверяется на эндпоинте `/view`:
```
@app.get("/view")
def view():
    if not request.headers.get("From-Fetch", ""):
        return "Use fetch", 400
    return request.args.get("html", "")
```
Таким образом у нас есть XSS sink, но его можно эксплуатировать только при наличии заголовка `From-Fetch` в запросе. Таким образом просто передав боту ссылку `/view` он получит `400` в ответе (другой домен передать нельзя, тк у куки с флагом стоит атрибут `domain`).
Здесь следует вспомнить или нагуглить о кэшировании в браузере. Можно заметить следующее интересное поведение браузера (по крайней мере Chromium):
1. Перейти на `/view?html=<XSS payload>`
2. Перейти на `/?html=<XSS payload>`
3. Нажать `Назад` в браузере
И ваш payload выполнится. Разберемся почему это работает.

Бот испольует Chromium и инфо далее будет относиться именно к этому движку. Поведение других браузеров может отличаться. При посещении веб-сайтов браузер часто должен загружать одни и те же файлы на разных страницах. Естественно, внедрение механизма кэширования дает огромные преимущества. В браузерах он называется дисковым кэшем (Disk cache).
В целях безопасности, необходимо обеспечить изоляцию кэшированных ресурсов между источниками. Мы не хотим, чтобы веб-сайт с кросс-доменным доступом мог определить, кэширован ли определенный ресурс или нет, поскольку это может стать источником утечки информации о сессии пользователя в другом приложении. Для решения этой проблемы Chromium представил разделенный дисковый кэш. При разделенном кэшировании записи в кэше получют ключ следующего вида: к URL-адресу добавляется префикс `_dk_`, за которым следует сериализованный ключ сетевой изоляции (полученный из сайта верхнего уровня и сайта фрейма), опционально дополнительные префиксы навигации, а затем URL ресурса.
Например, наш фрейм верхнего уровня — `example.com`, и он отображает youtube.com, то ресурс для `https://youtube.com/favicon.ico`, кэшированный с `youtube.com`, будет иметь ключ, который выглядит примерно так: `_dk_https://example.com https://youtube.com https://youtube.com/favicon.ico`
В некоторых случаях к ключу записи в кэше после `_dk_` добавляется префикс `cn_`. Он добавляется при выполнении следующих условий:
1. Определен инициатор запроса
2. Запрос является навигацией по мэйнфрейму
3. Инициатор запроса с другого сайта
Префикс `cn_` разделяет дисковый кэш таким образом, чтобы ответы, полученные в результате межсайтовой навигации по мэйнфреймам, хранились отдельно от запросов внутри одного сайта и запросов, не связанных с навигацией. Таким образом снижается риск отравления дискового кэша при межсайтовых запросах.

Первое требование не может быть выполнено, когда мы начинаем новую навигацию, например, вводим URL в адресной строке. По мере просмотра страниц, перехода по ссылкам и получения перенаправлений на стороне клиента, инициатор запроса будет постоянно меняться на предыдущую страницу, которая инициировала навигацию. Важно отметить, что редиректы `3XX` НЕ изменяют значение инициатора. Это означает, что если ввести URL в адресную строку, и бразуер перенаправит запрос на другой веб-сайт, то инициатор останется равным `null`.

При нажатии `Назад` в браузере вызывается функция `history.back()`, и браузер должен восстановить значение инициатора. То есть, если мы сначала перейдем на `google.com`, у нас будет нулевой инициатор. Если мы затем посетим `youtube.com`, наш инициатор будет установлен как `google.com`, но если мы нажмем кнопку `Назад` в браузере, мы вернемся на `google.com` с инициатором, снова установленным на `null`. В контексте задания, первоначально мы посетили `/view?html=<XSS payload>`, где хранилась запись дискового кэша для нашей навигации. Поскольку это была новая навигация с мэйнфрейма, инициированная браузером, инициатор был `null`, и поэтому запись кэша была создана без префикса `cn_`. Затем мы посетили `/?html=<XSS payload>`, где была получена запись `/view?html=<XSS payload>`, и поскольку это не навигация с мэйнфрейма, она также не использовала префикс `cn_`, поэтому предыдущая запись кэша была обновлена ​​полезной нагрузкой. Когда мы запустили `history.back()`, мы восстановили значение инициатора на `null` и, таким образом, загрузили ресурс, содержащий полезную нагрузку.

Теперь разберемся, как можно эксплуатировать подобное поведение браузера. Чтобы получить флаг нам нужны две вещи:
1. Заставить бота посетить `/?html=<XSS payload>` для заполнения кэша
2. Посетить `/view?html=<XSS payload>` с инициатором, установленным на `null`
Чтобы достичь скрипт с автоматизацией должен выполнить следующую последовательность событий:
1. Перейти на сайт задания (инициатор будет равен `null`)
2. Перейти на (выполнить `window.open()`) `/?html=<XSS payload>`, чтобы заполнить кэш
3. Перенаправить бота на другую страницу, сохранив инициатор `null` в истории
4. Выполнить `history.back()` для восстановления инициатора `null`
5. Перенаправить на `/view?html=<XSS>`
Чтобы вызов `history.back()` выполнял перенаправление, а не использовал дисковый кэш или `bfcache`, необходимо установить заголовок `Cache-Control: no-store`.
Важный нюанс: вместо `window.open()` лучше использовать ```PAYLOAD.replace('`', '%60').replace('{', '%7B').replace('}', '%7D').replace('<', '%3C').replace('>', '%3E')```, поскольку URL навигации верхнего уровня кодировал эти значения, а `fetch()` запрос - нет. Это может привести к несоответствию ключа кэша, и поэтому для активации уязвимости потребовалось закодировать эти значения в URL, чтобы ключи совпадали.
