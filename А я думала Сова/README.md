# А я думала Сова
**CyberCTF 2026**

Задание сделано по мотивам исследования [WAF Bypasses via h2 framing](https://lab.ctbb.show/research/h2-WAF-Bypasses). Перед нами промо-сайт мультфильма: таймер до премьеры и небольшое API. Беглый осмотр страницы ничего интересного не даёт — на лендинге только обратный отсчёт и постер, ссылок на флаг нет. Значит, идём в API.

Самый любопытный эндпоинт — `POST /api/wish`. Если изучить код приложения, видно, что он берёт тело запроса целиком, считает его путём к файлу и пытается этот файл прочитать:

```python
requested_path = request.get_data(as_text=True).strip()
target_path = os.path.join("/app/public", requested_path)
with open(target_path, "rb") as file:
    ...
```

Проверки на выход за пределы `/app/public` здесь нет, а `os.path.join` спокойно пропускает `..`. То есть перед нами классический path traversal: телом `../secret/flag.txt` можно прочитать флаг, лежащий в `/app/secret/flag.txt`. Казалось бы, задача решена — но не всё так просто.

Пробуем отправить запрос напрямую:

```bash
curl -k -i https://127.0.0.1:8443/api/wish \
  -X POST \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data '../secret/flag.txt'
```

В ответ прилетает `403 Forbidden` с текстом *Request forbidden by administrative rules* — это фирменная заглушка HAProxy. Payload правильный, но до приложения он даже не доезжает: что-то режет запрос на границе.

Если же отправить `POST /api/wish` вообще без тела, запрос проходит и приложение честно отвечает `{"status": "empty"}`. Вывод напрашивается сам собой: блокируется не путь и не сам эндпоинт, а именно наличие тела в запросе. Перед нами WAF, который реагирует на содержимое body.

Заглянув в конфигурацию стенда, подтверждаем догадку. Перед приложением стоит HAProxy, а проверкой занимается Coraza — причём не внутри прокси, а отдельным процессом, к которому HAProxy обращается по протоколу SPOE. Правило у WAF ровно одно и максимально жадное:

```
SecRule REQUEST_BODY "@rx .+" "id:100000,phase:2,deny,status:403"
```

Любое непустое тело — мгновенный `403`. В лоб его не обойти: менять путь бесполезно, менять содержимое бесполезно, правило смотрит на сам факт наличия тела. Нужно подойти с другой стороны.

Ключевой момент — **когда** именно HAProxy спрашивает у WAF разрешение. Проверка навешана так, что срабатывает сразу после разбора заголовков запроса:

```
http-request send-spoe-group coraza coraza-req
http-request deny deny_status 403 if { var(txn.coraza.action) -m str deny }
```

В SPOE при этом передаётся тело — `body=req.body`. Для HTTP/1.1 всё честно: там заголовки и тело приходят одним сплошным потоком, поэтому к моменту проверки тело уже лежит в буфере, правило его видит и запрос отклоняется. Именно поэтому обычный `curl` выше получает `403`.

А вот HTTP/2 устроен иначе. Запрос в нём разбит на отдельные бинарные фреймы: `HEADERS` несёт метод, путь и заголовки, а `DATA` — тело. И эти фреймы можно отправить **не одновременно**, а с паузой между ними.

Что произойдёт, если отправить `HEADERS` и немного подождать, прежде чем слать `DATA`? HAProxy получает заголовки, видит, что это начало запроса, и тут же дёргает WAF. Но тела-то ещё нет — `DATA` в пути. Coraza получает пустое `req.body`, правило `@rx .+` ни на что не матчится, вердикт — **allow**. HAProxy фиксирует это решение и начинает проксировать запрос на бэкенд. Когда следом приходит `DATA` с нашим путём, тело просто дотекает до приложения — повторной проверки уже не будет.

```
T+0.0s   клиент → HEADERS (POST /api/wish, END_STREAM не выставлен)
T+0.0s   HAProxy → Coraza: req.body пустой → ALLOW
T+0.0s   HAProxy решает форвардить запрос на бэкенд
T+0.7s   клиент → DATA: "../secret/flag.txt"
         тело уходит на Flask → path traversal отрабатывает → флаг
```

Это и есть body timing gap из статьи: out-of-process WAF принимает решение по неполному запросу и уже не может его пересмотреть. Самое коварное — в логах Coraza срабатывание всё-таки появится (тело-то в итоге проходит через движок), но вердикт опоздает: клиент к этому моменту уже получит свой `200`.

Пауза между фреймами должна быть чуть больше, чем `timeout processing` у SPOE-агента (в стенде это `500ms`). Поэтому в солвере стоит задержка `0.7s` — инспекция гарантированно успевает завершиться на пустом теле раньше, чем долетит `DATA`.

### Собираем эксплойт

Руками такое через `curl` не сделать: он всегда шлёт `HEADERS` и `DATA` вплотную, так что для него H2-запрос ничем не отличается от H1 и ловит `403`. Нужен клиент, который умеет управлять фреймами вручную — для этого и написан `solver/h2_bypass.py` на библиотеке `h2`. Логика простая:

1. Поднять TLS-соединение с ALPN `h2` и отправить HTTP/2-преамбулу.
2. Отправить `HEADERS` для `POST /api/wish` с `end_stream=False` — то есть «заголовки есть, но запрос ещё не закончен».
3. Выждать паузу (`--delay`, по умолчанию `0.7`).
4. Отправить `DATA` с телом `../secret/flag.txt` и `end_stream=True`.
5. Прочитать ответ и достать флаг из поля `content`.

```bash
python solver/h2_bypass.py --host 127.0.0.1 --port 8443 --delay 0.7
```

В ответ прилетает `200` и JSON, где в `content` лежит содержимое `/app/secret/flag.txt` — флаг.

### Что ещё стоит знать

- **Менять `Content-Type` на `multipart/form-data` или JSON бесполезно.** Это другой известный обход Coraza (такие тела не попадают в `REQUEST_BODY`), но в стенде он закрыт: процессор тела принудительно переведён в `URLENCODED`, так что сырое тело снова видно правилу. Рабочий путь остаётся один — тайминг фреймов HTTP/2.
- **GET-запросы и прямое чтение не помогут.** `GET /api/wish` вернёт `405`, а статика Flask каталог `secret` наружу не отдаёт.
- Короткая задержка (меньше `500ms`) не сработает: WAF успеет дождаться тела и всё-таки вернёт `403`.
