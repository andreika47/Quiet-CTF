# Ворона и решетчатый сыр
**CyberCTF 2026**

В задании реализован генератор, который строит случайную решётку в
160-мерном пространстве, прячет в ней точку, сдвигает её на маленький
вектор и шифрует флаг ключом, выведенным из этого сдвига. Нам даны
базис решётки, сдвинутая точка и зашифрованный флаг. Нужно найти
сдвиг.

Вот всё, что делает `challenge.py` по существу:

```python
M, N, Q, CHEESE_BOUND = 160, 80, 4093, 5

a_prime = [[rng.randrange(Q) for _ in range(M - N)] for _ in range(N)]
basis   = public_basis(a_prime)          # строки [I_N | A'] и [0 | Q·I]
hole    = [rng.randrange(Q) for _ in range(N)]
cheese  = [rng.randint(-CHEESE_BOUND, CHEESE_BOUND) for _ in range(M)]
point   = lattice_point(hole, a_prime)   # hole · [I_N | A'] mod Q
target  = [(p + c) % Q for p, c in zip(point, cheese)]

key = sha256(DOMAIN + b"|" + " ".join(map(str, cheese)).encode())
ct  = flag XOR sha256-поток от key
```

Из кода видно, что решётка — это все векторы вида `x · [I | A'] mod Q`
плюс всё, что кратно `Q`. Такие решётки называются q-арными, и это
ровно та конструкция, которая лежит под LWE. Вектор `target` — точка
решётки `point` плюс сдвиг `cheese` с координатами от `−5` до `5`.
Ключ зависит только от `cheese`, так что искать нужно именно его.
Можно искать и `hole`: зная его, `cheese` считается как
`target − hole·[I | A'] mod Q` с приведением в `[−Q/2, Q/2)`. Это одна и
та же задача, записанная с двух сторон.

Вся случайность берётся из
`secrets.SystemRandom` и после записи `challenge.json` пропадает;
`challenge.py` сообщает нам только распределения — решётка случайная,
сдвиг равномерный на `[−5, 5]`. Никаких сидов, никаких слабых
генераторов, никакого «забытого» отладочного вывода.

Прежде чем что-то делать, стоит понять, корректна ли задача вообще —
то есть единственна ли точка решётки, из которой `target` можно
получить маленьким сдвигом. Для этого полезно оценить, насколько
близко друг к другу стоят точки решётки. Определитель решётки равен
`Q^(M−N) = 4093^80`, а для случайной решётки длина кратчайшего
ненулевого вектора хорошо предсказывается гауссовой эвристикой:

```text
λ₁ ≈ sqrt(M / (2πe)) · det^(1/M) ≈ 3.06 · 64 ≈ 196
```

Это и есть расстояние между соседними «дырками» в сыре. Область
вокруг точки решётки, из которой эта точка ближайшая, — её ячейка
Вороного; она заведомо содержит шар радиуса `λ₁/2 ≈ 98`. Длина
сдвига `cheese` в среднем `sqrt(160 · 10) ≈ 40` (дисперсия одной
координаты, равномерной на `{−5..5}`, равна `10`). То есть `target`
сидит глубоко внутри ячейки своей дырки, и ближайшая точка решётки
к нему — ровно `point`. Задача называется BDD, Bounded Distance
Decoding: найти ближайшую точку решётки, когда заранее известно, что
она намного ближе, чем все остальные.

Казалось бы, раз ближайшая точка одна, бери и ищи. Проблема в том,
каким базисом нам её дали. В `basis` лежат 80 строк вида
`(e_i, A'_i)` с координатами до `4093` и 80 строк вида `Q·e_j`.
Если попробовать «округлить» `target` в таком базисе (это метод
Бабаи: раскладываем вектор по базису с вещественными
коэффициентами, округляем их до целых), ошибка округления будет
порядка `Q/2 ≈ 2000` по каждой координате — в четыреста раз больше,
чем нужный нам сдвиг. Базис хороший только в одном смысле: он
порождает нужную решётку. Для декодирования он бесполезен, и это
нормально — именно такой базис и получает Лисица.

Стандартный план для подобных задач выглядит так. Сначала
переписываем задачу, чтобы искомое стало необычно коротким вектором
какой-то решётки. Потом прогоняем базис этой решётки через алгоритм
редукции — он вернёт другой базис той же решётки, но с короткими и
почти ортогональными векторами. Потом смотрим на первые строки
результата: если всё сработало, искомое там и лежит. Первый и
третий шаги — дело техники, вся тяжесть во втором.

Первый шаг здесь — вложение Каннана. Дописываем к базису одну строку
и один столбец:

```text
[ b₀      0 ]
[ …       … ]
[ b₁₅₉    0 ]
[ target  S ]       S = 5
```

Строки этой матрицы порождают решётку на единицу большей размерности.
В ней есть вектор `(target, S) − (point + Q·k, 0) = (cheese, S)`
длиной около `39`, а все остальные ненулевые векторы не короче
`λ₁ ≈ 196`: они либо пришли из исходной решётки, либо содержат строку
`target` с коэффициентом по модулю хотя бы `2`, и тогда их последняя
координата уже `≥ 10`, а первые 160 — не меньше, чем у любого вектора
исходной решётки. Получается решётка, в которой один вектор в пять
раз короче всех прочих. Такая постановка называется unique-SVP, и
редукционные алгоритмы находят такой вектор гораздо охотнее, чем
кратчайший вектор «честной» случайной решётки. Множитель `S`
выбирают порядка размаха координат сдвига: при `S = 1` редукция
получает возможность «дёшево» прибавлять к строке `target` кратные
самой себя, при `S ≫ 5` вектор `(cheese, S)` искусственно
удлиняется.

```python
rows = [row + [0] for row in basis] + [target + [bound]]
A = IntegerMatrix.from_matrix(rows)
```

Теперь про второй шаг. Чтобы понять, что делают LLL и BKZ, удобно
думать не о самих векторах базиса, а об их ортогонализации
Грама–Шмидта: `b_i*` — это `b_i` минус его проекция на предыдущие
векторы. Длины `‖b_1*‖, …, ‖b_d*‖` называют профилем базиса. Их
произведение всегда равно определителю решётки, то есть редукция
не может сделать все векторы короче — только перераспределить длины,
укоротив первые за счёт последних. У плохого базиса профиль похож на
обрыв: первые 80 значений около `4093`, остальные около `1`.
У хорошего — почти ровная линия. Редукция и занимается тем, что
выравнивает этот обрыв.

LLL — алгоритм Ленстры, Ленстры и Ловаса 1982 года — делает это самым
простым способом. Он идёт по базису и для каждого вектора `b_i`
сначала вычитает из него ближайшие целые кратные предыдущих векторов
(после этого `b_i` «почти ортогонален» предыдущим), а потом проверяет,
не стал ли он заметно короче своего соседа `b_{i−1}` в проекции:

```text
δ · ‖b_{i−1}*‖² ≤ ‖b_i*‖² + μ²_{i,i−1} · ‖b_{i−1}*‖²
```

Если условие нарушено — соседи меняются местами, и алгоритм
откатывается на шаг. При `δ = 0.99` это означает, что соседние
`‖b_i*‖` могут отличаться не более чем примерно в `1.16` раза, то есть
профиль становится пологим. Каждый обмен уменьшает некоторый
потенциал хотя бы на фиксированный множитель, поэтому алгоритм
гарантированно останавливается за полиномиальное число шагов. На
практике LLL для матрицы `161 × 161` работает две-три секунды.

Чего от LLL ждать? Теоретическая гарантия — первый вектор не длиннее
`det^(1/d)` более чем в `1.075^d` раз, но на случайных решётках он
ведёт себя заметно лучше: на практике `‖b₁‖ ≈ 1.022^d · det^(1/d)`.
Для `d = 161` и `det^(1/d) ≈ 62` это около `2000`. Именно столько мы
и получаем после LLL. Наш вектор длины `39` намного короче, но LLL
его не видит: его условие локальное, оно сравнивает только соседние
пары, и «протащить» короткий вектор через 160 позиций ему не на что
опереться.

BKZ, Block Korkine–Zolotarev, — это тот же LLL, у которого условие на
пару соседей заменено условием на блок из `β` соседних векторов:
первый вектор каждого блока должен быть кратчайшим в проекции этого
блока. Проверить такое условие — значит точно решить SVP в
размерности `β`, что делается перебором (enumeration) или решетом
(sieving). Алгоритм проходит по всем блокам подряд — это называется
туром, — в каждом блоке запускает SVP-решатель, вставляет найденный
короткий вектор на место и подчищает результат с помощью LLL. Туры
повторяются, пока базис меняется.

Параметр `β` — ручка «качество против времени». При `β = 2` это
просто LLL. При `β = d` первый вектор базиса — ровно кратчайший
вектор решётки, но перебор в размерности 161 не закончится никогда.
Между этими крайностями качество растёт плавно: практический
множитель `δ_β`, такой что `‖b₁‖ ≈ δ_β^d · det^(1/d)`, равен
примерно `1.0128` для `β = 20`, `1.0109` для `30`, `1.0097` для `40`.
Время же растёт экспоненциально по `β` (перебор — `2^{O(β log β)}`,
решето — `2^{0.292 β}`) и лишь полиномиально по `d`. Для fpylll в
один поток BKZ-20 — это секунды, BKZ-40 — минуты, BKZ-60 — часы.
На практике блоки запускают по возрастанию, `10 → 20 → 30 → …`, не
сбрасывая базис между запусками: каждый следующий блок стартует с уже
неплохого базиса и сходится быстрее. Так устроен и `solve.py`.

Здесь возникает естественный вопрос. По формуле выше BKZ-30 должен
дать `‖b₁‖ ≈ 1.0109^161 · 62 ≈ 350` — всё ещё в девять раз длиннее
нашего вектора. Почему же он его находит? Потому что формула про
случайную решётку, а у нас решётка с аномалией. Короткий вектор
«выпадает» не в начале базиса, а в конце: по мере того как редукция
выравнивает профиль, последние `‖b_i*‖` растут, и в какой-то момент
проекция `(cheese, S)` на последний блок оказывается короче, чем
`‖b_{d−β}*‖`. Тогда SVP-решатель на этом блоке её находит, а
LLL-подчистка за один тур перетаскивает вектор в первую строку.
Снаружи это выглядит как скачок: `‖b₁‖` падает с `≈ 700` сразу до
`39`, а не плавно. Момент скачка хорошо предсказывается оценкой
Alkim–Ducas–Pöppelmann–Schwabe:

```text
σ · sqrt(β)  ≲  δ_β^(2β − d) · det^(1/d)
```

где `σ ≈ 3.2` — среднеквадратичное одной координаты сдвига. Для
`β = 30` правая часть около `21`, левая около `17.5` — почти впритык;
для `β = 40` правая около `28`, левая около `20` — с запасом. Так что
на части экземпляров BKZ-30 успеет, а на части — нет, зато BKZ-40
проходит всегда.

Так и получается на практике. Четыре случайных экземпляра, fpylll
0.5.9 из Sage, один поток, по восемь туров на блок: после LLL
`‖b₁‖ ≈ 1850`, после BKZ-10 около `1000`, после BKZ-20 около `720` —
вектора нет. BKZ-30 за 11–15 секунд на двух экземплярах из четырёх
выдал `±(cheese, 5)` первой строкой, на двух других остановился на
`≈ 620`. BKZ-35 там не помог. BKZ-40 за три минуты нашёл вектор на
всех оставшихся. Если бы граница сдвига была `3`, хватило бы BKZ-20;
при `4` стабильно работал BKZ-30; при `6` BKZ-40 за восемь туров
вектор уже не нашёл. Пятёрка выбрана как рабочая точка: LLL и BKZ-20
заведомо мало, BKZ-30 или BKZ-40 решают за минуты.

Остаётся прочитать ответ. После каждого этапа редукции просматриваем
строки: нам нужна та, у которой последняя координата равна `±5`.
Если там `−5`, умножаем всю строку на `−1` — редукция не различает
вектор и его противоположный. Первые 160 координат — кандидат на
`cheese`; проверяем, что все они по модулю не больше `5`, собираем
ключ и поток ровно так же, как `challenge.py`, расшифровываем и
смотрим, похож ли результат на флаг.

```python
for i in range(A.nrows):
    row = [A[i, j] for j in range(m + 1)]
    if abs(row[m]) != bound:
        continue
    sign = 1 if row[m] == bound else -1
    e = [sign * v for v in row[:m]]
    if max(map(abs, e)) > bound:
        continue
    pt = decrypt(ct, e)
    if FLAG_RE.fullmatch(pt):
        return pt
```

Пара мелочей, на которых легко споткнуться. `target` дан по модулю
`Q`, и это правильно: в решётке есть `Q·ℤ^M`, так что ничего
«центрировать» перед вложением не нужно, а вот если вычислять
`cheese` как `target − point` без приведения по модулю, получится
мусор. И не стоит пугаться, если BKZ-30 ничего не нашёл: это
ожидаемо примерно в половине случаев, нужно просто дождаться
BKZ-40.

Пример скрипта решения: `solve.py`.

```bash
sage -python solve.py crow-lattice-cheese/challenge.json
# или, если fpylll стоит в системном Python:
python3 solve.py crow-lattice-cheese/challenge.json
```

Скрипт делает LLL, затем прогрессивный BKZ по блокам
`10 → 20 → 30 → 40 → 50`, после каждого шага ищет строку с `±5` в
конце и пробует расшифровать. На ноутбуке это от 30 секунд до
четырёх минут в зависимости от экземпляра.
